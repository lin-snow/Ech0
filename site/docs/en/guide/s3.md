---
title: Object storage (S3)
description: S3-compatible storage and the admin panel options
---

Once enabled, attachments can be written to **S3-compatible object storage** (AWS S3, MinIO, Cloudflare R2, Alibaba Cloud/Tencent Cloud, and other services compatible with the S3 API), easing the load on local disks and making CDN setups easier.

---

## Before enabling

Prepare the following from your cloud provider or self-hosted service:

1. **Bucket name**
2. **Access Key / Secret Key** (or the provider's equivalent credentials)
3. **Endpoint**: the API access address given by the provider (for example `s3.ap-southeast-1.amazonaws.com` or your MinIO address)
4. If you use an **AWS regional endpoint**, you usually also need the **Region**

---

## Admin panel options (item by item)

### Enable S3

The master switch. When off, local (or default) storage is used; when on, the following options appear.

### Enable SSL

Recommended to **stay on**, so keys and data are not sent in plaintext over the wire.

### S3 service / template

Choose a provider template (such as **AWS S3**, **MinIO**, **Cloudflare R2**, **Other**) to prefill some defaults; with **Other**, verify the Endpoint format yourself.

### S3 Endpoint

Enter the **API Endpoint** provided by the provider. Generally **do not** write an `http://` or `https://` prefix inside the field (follow the hint in your interface; some interfaces use a switch for SSL instead).

### Access Key / Secret Key

The API credential pair; the secret is visible only to you, so never leak it.

### Bucket

The name of the bucket where objects are stored; create it in the console beforehand.

### Path Prefix (optional)

If you enter `prod/ech0`, every object key is prefixed with it, making it easy to isolate multiple environments in one bucket. If left empty, objects go directly under the corresponding rule path at the bucket root.

### Region

Fill this in when using a template that requires a region, such as AWS (for example `ap-southeast-1`); for providers with purely path-style endpoints, follow their documentation or leave it empty.

### CDN / public access (if the interface provides it)

If attachments need to be served through a CDN or a fixed domain, configure the **CDN domain** or **public read policy** in the interface; otherwise browsers may fail to load images/media directly. The **bucket or CDN policy** must allow cross-origin uploads from your site's domain (if you see CORS errors during direct browser uploads, configure CORS on the storage or gateway side).

---

## Permissions and policies

The key used for uploads must at minimum be able to perform the following on the target bucket: **list, upload, read, delete** (the exact action names vary by provider). If saving reports **Access Denied**, check:

- whether the Access / Secret is wrong;
- whether the IAM/policy is restricted to the wrong bucket or path;
- whether the bucket name, Region, and Endpoint are mixed up (for example, an OSS endpoint entered into an AWS template).

---

## Relationship to "Data control"

Operations such as changing buckets, migrating between local and object storage, or bulk-fixing URLs carry high risk; **back up** your database and files completely before doing them, and validate in a test environment before going to production.

---

## FAQ

**Is Path Prefix required?**  
No; filling it in makes it easier to isolate multiple projects in one bucket.

**Everything is configured correctly, but uploads still fail?**  
Open the browser developer tools and check for **CORS** errors; if there are any, configure the object storage or the fronting gateway to allow your site's origin.

**Media won't open?**  
Check the **public read** or **signed URL** policy for the bucket/objects, and whether you changed the Endpoint/CDN without updating the access addresses recorded in the database.
